## Context

当前仓库已经具备多条 runnable baseline workflow，但最关键的用户主入口仍然是一个临时性质很强的自然语言链路：Discord 消息经过关键词式 politburo 分流后，要么直接回复，要么落到 `web_research` / `intel_update` 这类 baseline workflow。这个实现对“基础功能是否可跑”已经足够，但与设计书中“总书记 -> 政治局 -> 国务院 -> 书记处 -> 评估/改进”的治理式中枢相差很远。

当前最突出的偏差有三类：

- 对话入口仍是 route-oriented，而不是治理-oriented：系统先问“打哪条 workflow”，而不是先判断任务类型、目标、约束、所需研究深度与是否需要审议。
- 研究输出仍是 workflow-oriented，而不是 artifact-oriented：返回给用户的是 route/task/workflow 信息，而不是结构化结论、证据、风险与后续动作。
- 质量控制仍是 smoke-oriented，而不是 production-oriented：缺少对话数据集、路由正确率、来源质量、回答可用性、版本回放与回归门槛。

这次 change 的目标不是“一次性实现整本设计书”，而是建立一个正式的下一阶段模板：先把最重要的单链路做深，且让它天然包含书记处归档、中纪委评估、中组部改进所需的运行时基础。

## Goals / Non-Goals

**Goals:**
- 把“总书记输入 -> 政治局任务澄清 -> 国务院研究编排 -> 书记处留档 -> 面向用户答复”定义成正式主链。
- 定义该主链依赖的 runtime foundation，包括 trace、版本、证据、结构化 artifact、失败回退与可回放能力。
- 定义面向对话链的评测体系，使后续优化可以通过样本、分数与回归门槛驱动，而不是靠主观体验。
- 明确分阶段交付顺序，使后续实现优先补“基建 + 单链路质量”，而不是继续横向增加 workflow 数量。

**Non-Goals:**
- 本 change 不要求一次性把所有部委子图、常委盘中巡检、法院执行分析等全部实装。
- 本 change 不要求立即引入新的大型外部基础设施。
- 本 change 不要求直接完成自动改进上线流程，只定义其前置基础。
- 本 change 不替代现有 workflow baseline，而是把它们下沉为正式主链可调用的执行单元。

## Decisions

### 1. 下一阶段以“政治局对话主链”作为旗舰链路
正式设计的第一优先级不是再补新的 workflow，而是把最常用、最能暴露系统质量的入口做成旗舰链路。

选择原因：
- 用户直接感知质量的地方首先是对话入口，而不是内部 workflow 数量。
- 设计书明确把总书记输入、政治局澄清、国务院执行、书记处归档当成顶层骨架。
- 单链路做深后，才能成为盘前、盘中、盘后、夜间链的复用模板。

备选方案：
- 继续以 `intraday_watch` 或 `nightly_improvement` 为主轴。放弃，因为这些链路虽然重要，但不是当前最强用户感知入口。
- 同时并行改所有 workflow。放弃，因为会稀释基建与质量闭环的精力。

### 2. 对话入口先做“任务治理”，再做“研究执行”
自然语言入口必须先产出结构化任务澄清对象，再决定走哪条研究或执行链路。

选择原因：
- 设计书强调政治局负责问题定义、目标、约束与优先级，而不是简单路由。
- 现在的关键词分流把“研究一下美国加降息情况”错误简化成网页搜索，这正是缺少任务治理层的结果。
- 结构化任务对象是后续书记处留档、中纪委评分和中组部改进的共同前提。

备选方案：
- 继续沿用关键词 dispatcher，只增强 pattern。放弃，因为会继续把核心问题压缩成“文本分类”。
- 让 LLM 直接给最终答案，中间不留 artifact。放弃，因为不符合设计书的可审计、可追溯原则。

### 3. Runtime foundation 先围绕 artifact 与 provenance 建立
下一阶段的基建重点不是再加一层抽象，而是让每次对话都留下可追溯的结构化对象。

核心对象应至少包括：
- `DialogueIntent` / `TaskBrief`
- `ResearchPacket` / `EvidenceBundle`
- `DecisionDraft` / `UserReply`
- `RunTrace` / `VersionStamp`

选择原因：
- 设计书强调“所有 Agent 输出必须结构化”与“书记处统一留档”。
- 只有 artifact 完整，后续评分、归档、回放与改进才能成立。

备选方案：
- 先只加日志，不定义 artifact。放弃，因为日志无法替代结构化业务对象。
- 先实现复杂记忆系统。放弃，因为在 artifact 还不稳定时，记忆只会放大混乱。

### 4. 检索与研究必须来源治理优先，而不是“搜到就用”
正式主链中的研究步骤必须优先使用可信来源分层、query rewrite、证据筛选和失败回退。

选择原因：
- 当前 `web_research` 结果已经证明通用网页搜索无法承载宏观/政策/投研问题。
- 设计书中的系统不是通用聊天机器人，而是投研中枢，来源治理属于基础设施，不是锦上添花。

备选方案：
- 继续使用开放网页搜索 + 简单摘要。放弃，因为低相关结果会直接破坏用户信任。
- 一开始就接所有外部数据源。放弃，因为会扩大接入面，延迟主链质量闭环。

### 5. 评测体系必须先于大规模 prompt/skill 迭代
后续任何对话主链优化都必须被样本集、评分维度和回归门槛约束。

最低评测维度：
- 路由/任务澄清正确率
- 检索与证据相关性
- 结构化 artifact 完整性
- 最终回复可用性与一致性
- 回退路径是否安全

选择原因：
- 设计书明确要求“评估 -> 提案 -> 测试 -> 审批 -> 上线”。
- 如果没有评测基线，对话优化会退化成不断改 prompt 的经验主义。

备选方案：
- 先做功能，再补评测。放弃，因为当前已经进入质量阶段，不再是骨架阶段。

## Risks / Trade-offs

- [单链路优先会推迟其它 workflow 的深挖] → Mitigation: 把旗舰链路的 artifact、trace、评测与来源治理设计成可复制模板。
- [对话主链范围膨胀成“重新实现整个系统”] → Mitigation: 严格限定为总书记/政治局主入口及其直接研究编排，不扩展到所有部委细节。
- [来源治理过严导致召回不足] → Mitigation: 采用分层来源策略和失败回退，而不是只允许单一来源。
- [结构化对象过多增加实现成本] → Mitigation: 第一阶段先定义少量高价值 artifact，避免一开始建全套对象森林。
- [评测体系建设拖慢短期体验修复] → Mitigation: 先用真实 bad-case 样本建立最小数据集，与链路优化并行推进。

## Migration Plan

1. 先为对话主链定义 specs：任务治理、runtime foundation、对话评测。
2. 基于 specs 新建 follow-on implementation change，优先实现 artifact、trace、query rewrite、来源治理与回答 synthesis。
3. 用真实 Discord bad cases 建立最小评测集，并让回归测试在本地和 CI 可执行。
4. 将现有 `web_research` / `intel_update` 逐步下沉为正式主链可调用的执行能力，而不是直接暴露给最终用户。
5. 在主链稳定后，再把同样的 artifact / 评分 / 审批模型复制到盘前、盘中、盘后与夜间链。

回滚策略：
- 保留现有 baseline workflow 入口，避免一次性替换全部用户路径。
- 新主链先以 feature-flag 或路由分层方式引入，必要时可退回现有 baseline。

## Open Questions

- “政治局任务澄清”是完全独立的 graph，还是作为 `api-service` 顶层 orchestration 层先落地？
- 对宏观/政策/公司/商品问题，来源治理是否需要分不同 source pack？
- 书记处归档第一阶段是否只归档结构化 artifact，还是同时保留原始网页/抓取快照？
- 对话链的最终输出是否必须带来源引用编号，还是先内部保留 provenance、对外按需展示？
